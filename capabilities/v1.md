# Vocabulário de capacidades — `capabilities/v1`

Este documento é a versão em prosa de `capabilities/v1.mjs`. Se os dois
divergirem, o módulo `.mjs` é a fonte da verdade — este arquivo existe para
quem está escrevendo ou revisando um pacote sem abrir o código.

## Por que o vocabulário é fechado

`metadata.capabilities` declara o que um agente pode fazer, não como ele faz.
Um valor fora da lista falha a validação — não é avisado, não é tolerado, não
passa com um warning. A razão é a mesma que justifica o campo existir: se
qualquer string vale, a fronteira de permissão deixa de ser uma fronteira e
vira documentação que ninguém testa.

Crescer este vocabulário — adicionar um alvo de leitura, um verbo novo — é
mudança de **versão** (`capabilities/v2`), nunca adição silenciosa dentro do
v1. Um pacote que declara `capability_vocabulary: capabilities/v1` tem a
garantia de que a lista abaixo não muda sob ele. Sem essa garantia, validar
contra o vocabulário não protege nada: o alvo que passou ontem pode parar de
existir hoje.

## Os dois alvos fechados

Só `read` e `write` são listas fechadas de valores — o resto de
`capabilities` é estrutura (booleano, lista de nomes, objeto com
`allow`/`deny`), não vocabulário.

### `capabilities.read`

| Valor | O que cobre |
|---|---|
| `repository` | Código e arquivos do próprio pacote ou do projeto onde o agente opera |
| `documentation` | Documentação do projeto — READMEs, specs, ADRs |
| `audit_trail` | Trilha de auditoria de execuções anteriores, do próprio agente ou de outros |
| `test_evidence` | Evidência de teste já produzida — relatórios, logs de execução, veredito |
| `database` | Dados vivos em banco |
| `web` | Conteúdo de fora do pacote, via rede |

### `capabilities.write`

| Valor | O que cobre |
|---|---|
| `code` | Produzir ou alterar código |
| `documentation` | Produzir ou alterar documentação |
| `test_evidence` | Produzir evidência de teste |
| `report` | Produzir relatório — de execução, de incidente, de status |
| `pull_request` | Abrir ou atualizar pull request |

Um valor que não está em uma destas duas listas — por exemplo `read:
internet` em vez de `web`, ou `write: deploy` quando o que existe é
`pull_request` — reprova a validação. Não existe correção automática para
isto: o pacote tem de nomear o alvo certo.

## Os campos de estrutura livre

Estes campos de `capabilities` não têm lista fechada porque o valor é
específico do pacote, não do vocabulário — fechar a lista aqui não
protegeria nada, porque o nome certo depende do que o pacote integra.

| Campo | Forma | O que valida |
|---|---|---|
| `execute.allow` / `execute.deny` | **globs de shell** (ex.: `"git log*"`, `"npm test*"`), não nome de ferramenta | que nenhum glob aparece nas duas listas ao mesmo tempo — `deny` vence quando colidem |
| `network` | `false`, **ou lista de domínio** | que, quando não é `false`, cada entrada é um domínio nomeado — nunca acesso irrestrito por omissão |
| `delegate` | lista de slugs de outro agente do mesmo pacote | que o slug referenciado existe no pacote |
| `approve` | lista de `id` de `human_gates` da `COMPANY.md` | que o `id` referenciado existe nos `human_gates` declarados |
| `budget` | `currency`, `monthly_cap`, `alert_at`, `alert_to` | tipo de cada campo — moeda, número, fração, destinatário |

Sobre `execute`: o glob é o **payload** carregado dentro da capacidade, não o
nome de uma tool. A tradução para tool de runtime é trabalho do binding —
em `bindings/claude-code.yml`, por exemplo, a capacidade `execute` inteira
mapeia para a tool `Bash`, e é o glob (`"git push*"`, `"sudo *"`) que decide
o que, dentro do Bash, é permitido ou negado. Escrever nome de tool
(`allow: [Bash, Read]`) em `execute.allow` inverte a camada: é exatamente o
vocabulário agnóstico de runtime que este campo existe para preservar.

Sobre `network`: `false` nega toda rede. A lista de domínio é o allowlist de
alvo autorizado — existe porque um papel como `pentest` precisa nomear o que
pode atingir, não apenas que "tem rede". Um emissor que não sabe expressar
uma lista de domínio no runtime de destino **reporta a perda com aviso
nomeado**, em vez de alargar a capacidade para a internet inteira em
silêncio — alargar sem avisar é o modo de falha que esse campo existe para
impedir.

Sobre `budget`: o mesmo formato de sub-campos aparece em **dois lugares**
com significado diferente — `metadata.budget` em `COMPANY.md` é o teto da
empresa inteira; `metadata.capabilities.budget` em `AGENTS.md` é o teto do
papel. Os dois convivem: o validador lê primeiro o teto do papel e só cai
para o da empresa quando o papel não declara o próprio. Ver `SCHEMA.md` §2
para a tabela das duas chaves lado a lado.

## Memória e contexto

Dois outros pontos do vocabulário, fora de `capabilities`, também são listas
fechadas em `v1.mjs`:

| Campo | Valores aceitos |
|---|---|
| `memory.scope` | `none`, `session`, `project`, `org` |
| `memory.retention` | `none`, `session`, `project`, `org` |
| `context.sources[].kind` | `repo_file`, `package_doc`, `url`, `path` |

## Alias pt-BR

`capabilities/v1.mjs` também exporta `ALIASES` — o mapa de chave em
português para a chave canônica em inglês que `normalizeAliases` (em
`tools/rules.mjs`) usa para reescrever `metadata.*` na leitura. Aceito na
leitura, nunca emitido na escrita: todo pacote novo escrito a partir deste
acervo usa a chave canônica; o alias existe para não quebrar pacote antigo
escrito em português.
